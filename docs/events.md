# 7. Event Model

This document defines the event model used by CommerceETLAV.

CommerceETLAV processes commerce events generated by the fictional retailer Prosperity Bazaar Empire (PBE).

The event model supports:

- Event generation and streaming.
- Event identity and ordering.
- Raw event ingestion and storage.
- Data transformation and SQL analytics.
- AI/ML analysis of unstructured text.
- Reproducible integration and end-to-end testing.

## 7.1 Purpose

This document defines the event model used by CommerceETLAV.

The event model provides a common representation for business activities generated by PBE and processed by CommerceETLAV.

### Design Principle

**Big Data / AI First:** Keep commerce minimal. Add business complexity only when needed to demonstrate Big Data, AI/ML, or architecture skills.

### Design Goals

- One common JSON schema for all event types.
- Simple serialization and deserialization in Java and Python.
- Unique and deterministic event identifiers.
- Ordered event streams within each dataset.
- Explicit timestamps for different processing stages.
- Structured fields for SQL analytics.
- Free-text client comments for AI/ML analysis.
- Minimal business validation for the MVP.
- Extensibility for advanced versions.

### Scope

The MVP supports seven event types representing one successful retail purchase lifecycle.

Advanced versions may introduce additional event types, business workflows, and data-processing requirements.

The business rules are defined in [business.md](business.md).

## 7.2 Event Architecture

### Event Definition

An event represents one business action or state transition in the retailer's system.

Examples:

- A Retail Client starts a session.
- A Retail Client creates an order.
- A product is added to an order.
- An order is submitted.
- A payment succeeds.
- An order is delivered.
- A Retail Client ends a session.

Each event is represented as a JSON object.

### Event Ownership

Every MVP event belongs to:

- One retailer tenant.
- One Retail Client.
- One Retail Session.
- One ordered dataset.

Order-related events also reference an order.

### Event Producer

For the MVP, Generator acts as a simplified event gateway.

It simulates receiving business events from PBE and publishes normalized events to Kafka.

The MVP does not implement a separate retail backend or external event-ingestion API.

In an advanced version, a gateway may receive events from multiple retailers and normalize different input formats.

### Event Processing Flow

```text

       |
       | Simulated commerce activity
       v

       |
       | Normalized JSON events
       v

       |
       v

       v

       |

       |
       v

       |
       v

       +--------------------+
       |                    |
```

Detailed service responsibilities and infrastructure are defined in the project architecture documentation.

## 7.3 Event Identity and Ordering

### Event Identity

Every event has two forms of identity.

| Identity | Fields | Purpose |
|---|---|---|
| Event ID | `eventId` | Globally unique logical event identifier |
| Composite Identity | `tenantId`, `datasetId`, `eventSequence` | Unique event position within an ordered dataset |

The composite identity is:

```text
(tenantId, datasetId, eventSequence)
```

Both identities refer to the same logical event.

### Tenant Identity

`tenantId` identifies the retailer using CommerceETLAV.

For the MVP, all events belong to Prosperity Bazaar Empire.

Advanced versions may support multiple retailers.

### Dataset Identity

`datasetId` identifies one logical ordered stream of events.

A retailer may have multiple datasets.

Each dataset has exactly one logical sequence owner.

A dataset is not necessarily a generation batch, session, order, or Kafka partition.

### Event Sequence

`eventSequence` identifies the position of an event within its dataset.

MVP rules:

- The first sequence number is `1`.
- Each subsequent event increments the sequence by `1`.
- Sequence numbers are unique within a dataset.
- Events are produced in sequence order.
- Different datasets have independent sequences.
- No global ordering is guaranteed across datasets.

Example:

| tenantId | datasetId | eventSequence | eventType |
|---|---|---:|---|
| PBE | PBE-ONLINE-01 | 1 | SESSION_START |
| PBE | PBE-ONLINE-01 | 2 | ORDER_CREATED |
| PBE | PBE-ONLINE-02 | 1 | SESSION_START |
| PBE | PBE-ONLINE-01 | 3 | ORDER_ITEM_ADDED |
| PBE | PBE-ONLINE-02 | 2 | ORDER_CREATED |

### Ordering Guarantee

For the MVP, Generator is responsible for:

- Assigning sequence numbers.
- Maintaining one logical sequence owner per dataset.
- Publishing events in sequence order.
- Avoiding duplicate or missing sequence numbers.

Kafka ordering is discussed in [Section 7.10](#710-kafka-integration).

### Deterministic Identity

The same generation seed and configuration should produce identical logical events.

This includes stable event identifiers and event sequences.

A separate `generationRunId` may identify an execution without changing logical event identity.

The exact identifier-generation algorithm will be defined before implementation.

## 7.4 Event Lifecycle and Timestamps

### Event Processing Stages

An event passes through multiple stages.

| Step | Stage | System | Timestamp / Metadata |
|---:|---|---|---|
| 1 | Business action occurs | Retailer | `occurredAt` |
| 2 | Business event is recorded | Retailer | `recordedAt` |
| 3 | Event receives stream position | Retail producer | `eventSequence` |
| 4 | Event is published | Retail producer / Gateway | `publishedAt` |
| 5 | Event enters CommerceETLAV | Gateway | `receivedAt` |
| 6 | Event is appended to Kafka | Kafka | Topic, partition, offset |
| 7 | Event is processed by Ingestor | Ingestor | `ingestedAt` |
| 8 | Raw event is persisted | MinIO | `storedAt` |

**Note:** In production, each timestep represents a distinct real-world step. \
For the MVP, Generator simulates all five pre-Kafka stages: \
the retailer's business activity, event recording, publication, and gateway receipt. \ 
Generator also assigns the actual event sequence and publishes the resulting event to Kafka. \

### Timestamp Definitions

| Field | Meaning | Owner |
|---|---|---|
| `occurredAt` | When the business action occurred | Retailer |
| `recordedAt` | When the retailer recorded the action | Retailer |
| `publishedAt` | When the event was published | Producer / Gateway |
| `receivedAt` | When CommerceETLAV received the event | Gateway |
| `ingestedAt` | When Ingestor processed the event | Ingestor |
| `storedAt` | When raw event persistence completed | Storage pipeline |

All timestamps use ISO 8601 UTC.

Example:

```text
2026-01-15T14:32:18.000Z
```

### Timestamp Ownership

Not every timestamp must be included in the original incoming event.

Processing timestamps may be added by the relevant CommerceETLAV service.

For the MVP, Generator simulates the retailer and gateway stages.

The exact timestamp ownership and persistence format will be finalized before implementation.

### Event Time vs Processing Time

Event time and processing time are different concepts.

Events may eventually arrive late or out of order.

The MVP assumes valid, sequential event generation.

Advanced versions may demonstrate event-time processing, late-arriving data, and processing delays.

## 7.5 Event JSON Schema

### Common Schema

All event types use one common JSON schema.

Fields that do not apply to a specific event type may be `null` or omitted, according to the final serialization rules.

### Identity Fields

| Field | JSON Type | MVP Required | Description |
|---|---|---|---|
| `schemaVersion` | Integer | Yes | Event schema version |
| `eventId` | String | Yes | Unique logical event identifier |
| `tenantId` | String | Yes | Retailer tenant identifier |
| `datasetId` | String | Yes | Ordered dataset identifier |
| `eventSequence` | Integer | Yes | Event position within dataset |
| `eventType` | String | Yes | Business event type |

### Business Fields

| Field | JSON Type | MVP Required | Description |
|---|---|---|---|
| `retailClientId` | String | Yes | Retail Client owning the event |
| `sessionId` | String | Yes | Retail Session identifier |
| `orderId` | String | Conditional | Order identifier |
| `productId` | String | Conditional | Product identifier |
| `quantity` | Integer | Conditional | Number of product units |
| `unitPrice` | Number | Conditional | Price per product unit |
| `totalAmount` | Number | Conditional | Total order payment amount |
| `currency` | String | Conditional | Currency code; `USD` in MVP |
| `destinationId` | String | Conditional | Delivery destination identifier |
| `channel` | String | Yes | `ONLINE` in MVP |
| `storeId` | String | No | Physical store identifier; future use |
| `clientEventComment` | String | No | Free-text comment associated with the event |

### Timestamp Fields

| Field | JSON Type | MVP Required | Description |
|---|---|---|---|
| `occurredAt` | String | Yes | Business action timestamp |
| `recordedAt` | String | Yes | Retailer recording timestamp |
| `publishedAt` | String | Yes | Publication timestamp |
| `receivedAt` | String | Yes | Gateway receipt timestamp |
| `ingestedAt` | String | No | Ingestor processing timestamp |
| `storedAt` | String | No | Raw persistence timestamp |

### Currency

The MVP supports only United States dollars.

```json
{
  "currency": "USD"
}
```

No currency conversion is required.

Advanced versions may support multiple currencies and currency conversion.

### Numeric Values

Proposed MVP constraints:

| Field | Rule |
|---|---|
| `schemaVersion` | Positive integer; initially `1` |
| `eventSequence` | Positive integer, starting at `1` |
| `quantity` | Positive integer |
| `unitPrice` | Nonnegative monetary value |
| `totalAmount` | Nonnegative monetary value |

The exact numeric limits and monetary representation will be finalized in a later revision.

### Example Event

Example `ORDER_ITEM_ADDED` event:

```json
{
  "schemaVersion": 1,
  "eventId": "EVT-000003",
  "tenantId": "PBE",
  "datasetId": "PBE-ONLINE-01",
  "eventSequence": 3,
  "eventType": "ORDER_ITEM_ADDED",
  "retailClientId": "CLIENT-001",
  "sessionId": "SESSION-001",
  "orderId": "ORDER-001",
  "productId": "PRODUCT-001",
  "quantity": 2,
  "unitPrice": 79.99,
  "currency": "USD",
  "channel": "ONLINE",
  "clientEventComment": "I need lightweight headphones for running.",
  "occurredAt": "2026-01-15T14:32:18.000Z",
  "receivedAt": "2026-01-15T14:32:18.000Z",
  "publishedAt": "2026-01-15T14:32:18.000Z",
  "recordedAt": "2026-01-15T14:32:18.100Z"
}
```

This example is illustrative.

The final field requirements and timestamp ownership will be defined in subsequent revisions.

## 7.6 Event Types

### MVP Event Types

The MVP supports seven event types.

| # | Event Type | Description | Event-Specific Fields |
|---:|---|---|---|
| 1 | `SESSION_START` | Retail Client starts a session | `sessionId` |
| 2 | `ORDER_CREATED` | Client creates a draft order | `orderId` |
| 3 | `ORDER_ITEM_ADDED` | Client adds an item to an order | `orderId`, `productId`, `quantity`, `unitPrice` |
| 4 | `ORDER_SUBMITTED` | Client submits an order for payment | `orderId` |
| 5 | `PURCHASE` | Payment succeeds | `orderId`, `totalAmount`, `currency` |
| 6 | `DELIVERED` | Order reaches its destination | `orderId`, `destinationId` |
| 7 | `SESSION_END` | Retail Client ends a session | `sessionId` |

Common required fields apply to every event type.

### MVP Event Sequence

```text
SESSION_START
      |
      v
ORDER_CREATED
      |
      v
ORDER_ITEM_ADDED
      |
      +---- Repeat for additional items
      |
      v
ORDER_SUBMITTED
      |
      v
PURCHASE
      |
      v
DELIVERED
      |
      v
SESSION_END
```

### Event-Specific Requirements

Each event type has a minimal set of applicable business fields.

Fields not relevant to an event type may be omitted.

Detailed requirements will be finalized in a later revision.

### Advanced Event Types

Possible advanced event types include:

- `ORDER_ITEM_REMOVED`
- `ORDER_DESTINATION_CHANGED`
- `ORDER_CANCELLED`
- `RETURN_REQUESTED`
- `RETURN`
- `REVIEW`
- `CLIENT_REGISTERED`
- `CLIENT_UPDATED`
- `CLIENT_DELETED`

These event types are not part of the MVP.

## 7.7 Business Relationships

### Entity Relationships

The MVP includes these relationships:

| Entity | Relationship |
|---|---|
| Retailer | Owns multiple Retail Clients |
| Retail Client | Has multiple sequential sessions over time |
| Retail Session | Contains exactly one order |
| Order | Contains one or more items |
| Order Item | References one product |
| Retail Client | Has one predefined delivery destination |
| Event | Belongs to one Retail Client and one session |
| Dataset | Contains an ordered sequence of events |

### Identifiers

Business identifiers are represented as strings.

Examples:

```text
tenantId        = PBE
retailClientId  = CLIENT-001
sessionId       = SESSION-001
orderId         = ORDER-001
productId       = PRODUCT-001
destinationId   = DESTINATION-001
```

Exact identifier formats will be finalized before implementation.

### Product Information

The MVP uses a predefined product dataset.

Events reference products through `productId`.

The Generator may use product attributes such as name, category, and price when generating events.

The final representation of product attributes in analytical tables will be defined during data transformation design.

## 7.8 Client Event Comments

### Field Definition

The free-text field is named:

`clientEventComment`

It represents a comment associated with the Retail Client's event.

### MVP Rules

- The field exists in the common event schema.
- It is optional.
- It may contain natural-language text.
- Generator produces synthetic comments.
- Comments may appear on any event type.
- No dedicated review event is required.

### Examples

| Event Type | Example Comment |
|---|---|
| `SESSION_START` | "Looking for accessories for my new laptop." |
| `ORDER_CREATED` | "Buying equipment for my home office." |
| `ORDER_ITEM_ADDED` | "I need headphones with good battery life." |
| `ORDER_SUBMITTED` | "Everything looks good for my office setup." |
| `PURCHASE` | "This should be useful for my daily work." |
| `DELIVERED` | "The package arrived this morning." |
| `SESSION_END` | "Finished shopping for today." |

These are synthetic examples, not mandatory comments for every event.

### AI/ML Use Cases

Client event comments can support:

- Sentiment analysis.
- Topic classification.
- Keyword extraction.
- Semantic similarity.
- Text clustering.
- Natural-language business insights.

AI/ML analysis may combine comments with structured event fields.

## 7.9 Event Generation

### Generator Responsibility

Generator produces synthetic commerce events using:

- Preconfigured Retail Clients.
- Preconfigured products.
- Preconfigured delivery destinations.
- Deterministic generation settings.
- Synthetic client event comments.

### Generation Configuration

Proposed configuration parameters:

| Parameter | Description |
|---|---|
| `seed` | Deterministic random seed |
| `eventCount` | Target number of generated events |
| `datasetCount` | Number of logical ordered datasets |
| `eventRate` | Target generation rate |
| `startTime` | Starting business timestamp |
| `clientCount` | Number of configured clients to use |
| `productCount` | Number of configured products to use |

Exact configuration APIs and constraints will be defined during Generator implementation.

### Determinism

Identical generation inputs should produce identical logical events.

This includes:

- Event identifiers.
- Event types.
- Business relationships.
- Event sequences.
- Event timestamps.
- Client event comments.

### MVP Assumptions

Generator produces only complete and valid business scenarios.

It does not simulate:

- Invalid events.
- Duplicate events.
- Missing data.
- Business failures.
- Parallel actions for the same client.
- Out-of-order publication within a dataset.

## 7.10 Kafka Integration

### Message Format

Each Kafka message contains one JSON commerce event.

### Message Key

The Kafka message key is:

`datasetId`

This allows events from the same dataset to be routed consistently to the same partition under a stable partitioning configuration.

### Partitioning

- One dataset has one logical sequence owner.
- Multiple datasets may share one Kafka partition.
- A dataset does not require a dedicated partition.
- Kafka preserves record order within a partition.
- Kafka does not guarantee global ordering across partitions.

### Event Ordering

Generator assigns `eventSequence`.

Kafka does not create or validate this field.

The MVP assumes events are published in sequence order.

Advanced versions may detect and handle duplicates, gaps, and out-of-order arrivals.

### Kafka Metadata

Kafka provides transport metadata such as:

- Topic.
- Partition.
- Offset.

This metadata is separate from business event identity.

## 7.11 Data Processing and Analytics

### Structured Analytics

Structured event fields support SQL analysis.

Examples:

| Analysis | Relevant Fields |
|---|---|
| Revenue over time | `occurredAt`, `totalAmount`, `currency` |
| Product popularity | `productId`, `quantity` |
| Average order value | `orderId`, `totalAmount` |
| Products per order | `orderId`, `productId`, `quantity` |
| Session duration | `sessionId`, `eventType`, `occurredAt` |
| Purchase funnel | `sessionId`, `eventType` |
| Delivery duration | `orderId`, `eventType`, `occurredAt` |
| Client activity | `retailClientId`, `eventType` |
| Event throughput | `datasetId`, processing timestamps |
| Dataset distribution | `tenantId`, `datasetId` |

Revenue calculations should use `PURCHASE` events to avoid counting the same order multiple times.

### AI/ML Analytics

AI/ML processing uses `clientEventComment`.

Examples:

- Identify frequently mentioned product requirements.
- Group comments by topic.
- Compare customer sentiment across product categories.
- Combine text insights with revenue and purchasing trends.

### Raw and Processed Data

Raw events preserve the incoming business data.

Processed analytical datasets may:

- Normalize field types.
- Extract business dimensions.
- Calculate derived metrics.
- Join events with product information.
- Enrich events with AI/ML results.

The exact analytical table schemas will be defined during the Analyzer milestones.

## 7.12 MVP Assumptions

The MVP assumes:

| Area | Assumption |
|---|---|
| Retailers | One retailer tenant |
| Sales Channel | Online only |
| Retail Clients | Preconfigured |
| Sessions | One active session per client |
| Orders | One order per session |
| Order Items | One or more items per order |
| Currency | USD only |
| Business Events | Seven supported types |
| Business Flow | Successful, sequential lifecycle |
| Event Validity | All generated events are valid |
| Event Uniqueness | No duplicate events |
| Required Fields | No missing required values |
| Producer Ordering | Correct sequence within each dataset |
| Business Failures | None |
| Payment Failures | None |
| Delivery Failures | None |
| Returns | Not supported |
| Cancellations | Not supported |
| Product Reviews | Not supported |
| Client Event Comments | Optional free text |

These assumptions keep the commerce model minimal.

They do not establish production-level reliability guarantees.
